CubyCrate stores application state in `/app/data`. A complete recovery also needs any storage outside that directory and any externally supplied secrets.

## What to protect

- SQLite database at `/app/data/db/cubycrate.db`, including its WAL state.
- Generated secrets in `/app/data/secrets/`, including `jwt.key` and `master.key` when present.
- Local file data under `/app/data/storage/`.
- Any host directories mounted as secondary storage nodes.
- S3-compatible buckets and externally supplied keys such as `CUBYCRATE_MASTER_KEY` or `CUBYCRATE_MASTER_KEY_FILE`.

<Aside type="danger" title="A database download is not a full backup">
  The administrator database backup contains SQLite metadata only. It excludes file blobs and secrets. Do not treat it as a disaster recovery archive.
</Aside>

## Create a cold full-volume backup

The application runbook recommends stopping the service before archiving the named volume. Run from the directory containing the same `compose.yaml` and environment used by the instance. The container restarts on exit from the script, including when archive validation fails after the stop succeeds.

```bash
set -Eeuo pipefail

BACKUP_DIR="${HOME}/cubycrate-backups"
mkdir -p "${BACKUP_DIR}"
TEMP_DIR="$(mktemp -d "${BACKUP_DIR}/.backup-XXXXXX")"
BACKUP_FILE="${BACKUP_DIR}/cubycrate-backup-$(date +%Y%m%d-%H%M%S)-$(basename "${TEMP_DIR}").tar.gz"
CONTENTS_FILE="${TEMP_DIR}/contents.txt"

docker compose stop cubycrate
trap 'docker compose start cubycrate; rm -f "${CONTENTS_FILE}"; rmdir "${TEMP_DIR}"' EXIT

docker run --rm \
  -v "${CUBYCRATE_VOLUME_NAME:-cubycrate_data}:/data:ro" \
  -v "${BACKUP_DIR}:/backup" \
  alpine tar -czf "/backup/$(basename "${BACKUP_FILE}")" -C /data .

tar -tzf "${BACKUP_FILE}" > "${CONTENTS_FILE}"
grep -Eq '^(.*/)?db/cubycrate\.db$' "${CONTENTS_FILE}"
grep -Eq '^(.*/)?storage/' "${CONTENTS_FILE}"
echo "Cold full-volume backup created and verified: ${BACKUP_FILE}"
```

Keep the archive encrypted and off the host. Inspect the archive listing carefully because it can contain authentication keys. Separately back up host-mounted storage, S3 buckets, and keys supplied outside the volume.

## Restore safely

Test restores only in a newly created isolated volume. Do not overwrite, reuse, or delete an existing production volume. Do not connect an isolated test container to production buckets, external storage mounts, or production credentials.

The application runbook supplies an isolated-volume restore procedure. Follow that procedure against the exact archive and release you intend to restore. Do not extract an archive over a mounted production data directory. Verify the database, secrets, and local storage before starting an isolated container, and keep the restored volume until an operator confirms it is disposable.

For production recovery, use a new target volume and restore only after isolated validation. Reconnect required external storage and the matching externally supplied keys before routing users to the instance.

## Updates and rollback

Before an update, take and verify a full backup. Use a published exact image tag, keep the existing data volume, and review that release's compatibility notes. Do not use `docker compose down -v` for routine updates or backups.

Direct in-place upgrade or rollback between historical CubyCloud `v0.0.1-alpha.1` data and CubyCrate `v0.0.1-alpha.2` is unsupported. Preserve historical volumes and backups separately. A future rollback requires a compatible CubyCrate image and a matching consistent backup of database, storage, and secrets.

## External storage coverage

- A volume archive includes local files inside the volume only.
- Back up secondary host-mounted paths separately.
- Back up S3-compatible objects using the provider's own backup or versioning facilities.
- Keep the master key needed to decrypt configured storage credentials. Losing it can make those credentials unusable.
